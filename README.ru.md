# OpsTrace

**Система контроля регулярных операционных процессов с подтверждением выполнения.**

[English documentation](README.md) · [Архитектура](docs/architecture.md)

OpsTrace помогает небольшой компании или команде описывать повторяющиеся процедуры, автоматически создавать задания по расписанию, фиксировать ответственного, прикладывать подтверждающие материалы и передавать результат на независимую проверку.

Это не просто список задач: задача становится принятой только после проверки результата. Существенные действия сохраняются в журнале аудита.

## Возможности

- **Рабочие пространства:** отдельные организации и команды с изоляцией данных.
- **Роли:** владелец, администратор, проверяющий и участник.
- **Регламенты:** ежедневная, еженедельная, ежемесячная, ежеквартальная и ежегодная периодичность.
- **Планировщик:** идемпотентная генерация экземпляров задач; повторный запуск не создаёт дубликаты.
- **Исполнение:** назначенный сотрудник начинает работу и отправляет результат на проверку.
- **Подтверждения:** вложения PDF, PNG, JPG/JPEG и WEBP размером до 10 МБ; сохраняется SHA-256.
- **Проверка:** результат принимается либо возвращается на доработку с обязательным комментарием.
- **Разделение обязанностей:** исполнитель не может принять собственный результат.
- **Журнал аудита:** история создания регламентов, генерации заданий и смены статусов.
- **Приватные файлы:** скачивание разрешено только аутентифицированному участнику соответствующего рабочего пространства.
- **Панель управления:** просроченные, активные, ожидающие проверки и ближайшие задания.

### Жизненный цикл задания

```text
OPEN → IN_PROGRESS → SUBMITTED → APPROVED
                         └──────→ REJECTED → IN_PROGRESS
```

Чтобы отправить работу на проверку, необходимо приложить хотя бы один файл. Возврат на доработку требует пояснения. Переходы выполняются в транзакциях и сопровождаются событиями аудита.

## Технологии

- Python 3.14

## Быстрый запуск через Docker

### 1. Подготовьте конфигурацию

```bash
cp .env.example .env
```

В Windows PowerShell вместо `cp` можно выполнить:

```powershell
Copy-Item .env.example .env
```

Замените `SECRET_KEY` и `POSTGRES_PASSWORD` на собственные значения. Пароль в `DATABASE_URL` должен совпадать с `POSTGRES_PASSWORD`.

Сгенерировать секрет Django можно так:

```bash
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

Для локального запуска значения `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` и `SECURE_SSL_REDIRECT=False` из примера подходят для `http://localhost:8000`. Не переносите эти параметры в production без настройки HTTPS.

### 2. Соберите и запустите сервисы

```bash
docker compose up --build -d
```

Compose поднимет PostgreSQL, веб-приложение и отдельный планировщик. Веб-процесс применит миграции, соберёт статику и запустит Gunicorn. Планировщик запускает генерацию заданий раз в час.

### 3. Создайте администратора Django

```bash
docker compose exec web python manage.py createsuperuser
```

Откройте:

- приложение: <http://localhost:8000>
- административную панель: <http://localhost:8000/admin/>
- health endpoint: <http://localhost:8000/health/>

Первое рабочее пространство создаётся через обычную регистрацию в приложении. Зарегистрировавшийся пользователь становится его владельцем. Django superuser предназначен для администрирования платформы и сам по себе не получает членство в рабочем пространстве.

### 4. Сгенерируйте задания вручную

Планировщик запускается каждый час. Для немедленной генерации выполните:

```bash
docker compose exec web python manage.py generate_work_items
```

Можно обработать все пропущенные даты до заданного дня:

```bash
docker compose exec web python manage.py generate_work_items --through 2026-11-03
```

Команда создаёт отсутствующие экземпляры от `next_due_date` до указанной даты включительно и перемещает следующую дату регламента вперёд. Уникальное ограничение базы данных защищает от повторной генерации одного экземпляра.

## Локальная разработка без Docker

### 1. Создайте виртуальное окружение

```bash
python -m venv .venv
```

Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

Linux/macOS:

```bash
source .venv/bin/activate
```

### 2. Установите зависимости и подготовьте `.env`

```bash
python -m pip install -r requirements/dev.txt
```

Скопируйте `.env.example` в `.env`. Для SQLite удалите или закомментируйте `DATABASE_URL`: без него приложение использует `db.sqlite3`. В локальном режиме оставьте `DEBUG=True` и `SECURE_SSL_REDIRECT=False`.

### 3. Примените миграции и запустите сервер

```bash
python manage.py migrate
python manage.py runserver
```

В отдельном терминале запускайте планировщик вручную:

```bash
python manage.py generate_work_items
```

## Проверки качества

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
pytest --cov=apps
ruff check .
```

Либо используйте команды `make install-dev`, `make run`, `make test`, `make lint` и `make check` из `Makefile`.

## Роли и права

| Возможность | Владелец | Администратор | Проверяющий | Участник |
|---|:---:|:---:|:---:|:---:|
| Просматривать все задания пространства | Да | Да | Да | Только назначенные |
| Создавать и изменять регламенты | Да | Да | Нет | Нет |
| Управлять участниками | Да | Да | Нет | Нет |
| Выполнять назначенную работу | Да | Да | Если назначен | Если назначен |
| Проверять отправленные результаты | Да | Да | Да | Нет |

В этой версии администратор добавляет уже зарегистрированный аккаунт по email. Токены приглашений и автоматическая отправка писем оставлены для следующего этапа, а не представлены как реализованная функциональность.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `SECRET_KEY` | Секрет Django; уникальный для каждой среды |
| `DEBUG` | Режим отладки; `False` в production |
| `ALLOWED_HOSTS` | Разрешённые имена хостов |
| `DATABASE_URL` | Строка подключения к БД; пустое значение включает SQLite |
| `CSRF_TRUSTED_ORIGINS` | Доверенные origins для CSRF |
| `SECURE_SSL_REDIRECT` | Перенаправление на HTTPS |
| `SECURE_HSTS_SECONDS` | Время действия HSTS |
| `EMAIL_BACKEND` | Backend исходящей почты |
| `DEFAULT_FROM_EMAIL` | Адрес отправителя |
| `LOG_LEVEL` | Уровень логирования |

## Перед production-развёртыванием

Репозиторий — production-oriented основа приложения, но не замена аудиту конкретной инфраструктуры. Перед использованием с реальными данными:

1. Установите `DEBUG=False`, задайте уникальный `SECRET_KEY`, строгие `ALLOWED_HOSTS` и HTTPS.
2. Настройте `SECURE_SSL_REDIRECT`, secure cookies, подходящую HSTS-политику и точный `CSRF_TRUSTED_ORIGINS`.
3. Используйте управляемый PostgreSQL, автоматические резервные копии, мониторинг и регулярную проверку восстановления.
4. Перенесите вложения в приватное объектное хранилище, сохранив проверку прав при скачивании.
5. Добавьте антивирусное сканирование и проверку фактического содержимого файлов. Текущий allowlist проверяет расширение и размер, но не заменяет антивирус.
6. Настройте SMTP, подтверждение email, восстановление пароля, приглашения и уведомления.
7. Добавьте централизованные логи, мониторинг ошибок, метрики и оповещения.
8. Выполните аудит зависимостей, тестирование безопасности и проверку требований хранения персональных данных.

Текущий Docker Compose рассчитан на локальную оценку и небольшие контролируемые установки. Для production нужны управляемые секреты, отдельные процессы web/scheduler, приватное постоянное файловое хранилище и документированный план резервного копирования и восстановления.

## Границы текущей версии

Реализовано: цикл «регламент → задание → подтверждение → проверка → аудит», изоляция рабочих пространств, базовое управление командой, приватная выдача файлов, PostgreSQL и CI.

Планируемые направления: email-приглашения и уведомления, часовые пояса для каждого пространства, настраиваемые сроки, объектное хранилище, антивирусная проверка, API, экспорт аудита и политики хранения данных. Они не включены в текущий функционал.
